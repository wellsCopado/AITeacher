# 网页物理光照：一个可选、实际运行的适配器

先用实际参考修轮廓、边缘、材料分层和连接。光追只能改善已有网格的遮挡、反射与光照，不能使错误模型变真实。不要把“真实感不足”一律诊断为缺少采样，也不要按所有主题强制增加渲染依赖。

本次台北101试制中，普通实时光照仍显平；采用同一自主网格、分离玻璃/金属、真实环境光，在最终Web内测试渐进光线追踪，并保留运动时的栅格预览。`assets/web/physical-viewer.mjs`是这次实际使用的代码，无课程、建筑或用户数据。

## 使用与边界

当前验证组合为 `three@0.186.1`、`three-gpu-pathtracer@0.0.27`、`three-mesh-bvh@0.9.15`、`xatlas-web@0.1.0`。从正规包源安装并固定锁文件。该版本的 `WebGLPathTracer` 已有弃用提示；这是本机已运行的兼容方案，不承诺未来版本或移动设备相同。升级时核实官方API并重验，不盲目消除警告或更换引擎。

```js
import { createPhysicalViewer } from './physical-viewer.mjs';

// 在最终GLB、纹理、环境光全部载入后准备。
const physical = createPhysicalViewer(renderer, scene, camera, reportStatus);
await physical.prepare();
controls.addEventListener('change', () => physical.reset());
// 动作/交互期间使用快速预览，停止后积累精细光照。
physical.render(isCameraMoving || isMechanismMoving);
// 切换外观/内部、改变网格可见性、暂停在新姿态后重新采集场景。
physical.updateScene();
// getState()给出当前实际渲染器、采样、开关和错误；卸载时dispose()。
```

`prepare()`与重采集会同步构建BVH，大网格可能短暂停顿；提供载入提示和可操作回退，先测目标设备再决定是否使用。勿在每帧重建场景。适配器将变更采集合并并延后900ms，先响应点击和镜头；准备期间使用真实栅格场景并报告updating，不能把旧快照当新光照。同步采集本身仍可能短暂阻塞，这不是无停顿或移动端通过。场景材质、区域灯初始化和HDR色彩空间由调用方负责。

不要直接调用 `setSceneAsync` 却遗漏BVH工作器；本次已因此发生回退。适配器使用当前已验证的同步采集。它检测浮点渲染能力，失败时继续可操作的栅格画面，并保留错误，不能只显示“精细画质”标签。

## 在真实网页核对

1. 静止后看实际玻璃/金属/接触影；转动后高光和遮挡应改变，不能是贴在表面的固定照片。
2. 旋转、缩放、换内部与底部，再播放、暂停在中间姿态；确认静态采集没有留下旧球、旧关节或隐藏物体。
3. 强制快速预览后继续操作，核对状态确实为raster；恢复精细光照后检查新姿态。采样数只说明累计渲染，不证明写实或帧率。
4. 最终生产构建再看同机位。保留实际截图、已见缺陷与设备范围；技术通过和用户视觉接受分开。

只参考搜索缩略图/标题也会制造科学错误。台北101检索中出现将外墙如意写成阻尼器的错误说明；应对照实际照片与业主/工程图，把装饰、结构和内部机制分清。图片不可达时记录未看，不把链接当看图证据。
